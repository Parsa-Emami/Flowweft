> به‌روزرسانی ۲۰۲۶-۱۰-۱۵: پایهٔ وب و رابط مرور رودمپ پیاده‌سازی شده است. ارزیابی زیر مربوط به خط مبنای برنامه‌ریزی پیش از این تغییر است؛ وضعیت فعلی در plans/progress.json و plans/web-roadmap.json ثبت می‌شود. موتور تخصصی و استقرار عملیاتی هنوز به شواهد مستقل نیاز دارند.

# بررسی محصول و مسیر عرضه — نسخهٔ ۰

تاریخ بررسی: ۲۰۲۶-۱۰-۰۱. مبنا: فایل v7 ارائه‌شده و مستندات رسمی منابع معرفی‌شده. کد اجرایی اپ در ورودی وجود ندارد؛ کیفیت اجرای نرم‌افزار یا آمادگی تولید را نمی‌توان از این بسته نتیجه گرفت.

این بررسی نیازسنجی اولیه و قضاوت مهندسی است؛ مصاحبهٔ کاربر، فروش، اندازهٔ بازار و product-market fit انجام/اثبات نشده‌اند. امتیازها احتمال موفقیت نیستند؛ اولویت عملی برای یک توسعه‌دهنده با ترجیح سربار عملیاتی کم‌اند. هدف، حل مسئلهٔ شخصی واقعی و سپس سنجش ارزش برای کاربران مشابه در سطح بین‌الملل است.

## FlowWeft: آیا ارزش ساخت دارد؟

**نسخهٔ batch/report مناسب‌تر از NDR زنده است؛ ML را بعد از baseline قابل‌اعتماد اضافه کن.** امتیاز عملی: 7.6/۱۰؛ اولویت ساخت: 4/۱۰. این امتیاز ترکیبی کیفی از وضوح مسئله، تمایز قابل‌دفاع، محدودشدن MVP، هزینهٔ عملیات و ریسک اعتماد/امنیت است؛ دقت آماری ندارد.

کاربر هدف: تحلیلگر مستقل، تیم شبکهٔ کوچک و پژوهشگر امنیت. مسئله: CSV و Zeek logs بزرگ خروجی پراکنده و بدون توضیح کافی دارند. کار موفقی که نرم‌افزار باید انجام دهد: گزارش قابل‌بازتولید از رفتار جریان و anomaly با حدود اعتبار.

وجود مسئله در این حوزه با وجود ابزارهای موجود سازگار است، ولی نیاز به این **محصول مشخص** هنوز فرضیه است. گزینه‌های جایگزین: Zeek، گزارش‌های سفارشی و ابزارهای NDR. فرضیهٔ تمایز: تحلیل offline/private batch با lineage و baseline روشن، بدون SIEM سنگین. اگر کاربر با جایگزین فعلی همین کار را آسان انجام می‌دهد، ویژگی بیشتر به‌تنهایی دلیل ساخت محصول نیست.

## نیازسنجی عملی پیش از عرضه

ابتدا یک وظیفهٔ واقعی تحت مالکیت خودت را با روش فعلی انجام بده و زمان، خطا، مراحل نصب و ریسک افشای داده را ثبت کن. سپس همان وظیفه را با MVP انجام بده. هدف آزمایشی پیشنهادی: کاهش حداقل ۳۰٪ زمان تکمیل، بدون خراب‌کردن صحت و قابلیت بازیابی؛ عدد هدف است، نه نتیجهٔ اندازه‌گیری‌شده.

برای آزمایش بیرونی، ۵ کاربر واقعاً مرتبط را انتخاب کن؛ این نمونه برای کشف مشکل UX است، نه تخمین کل بازار. از آنان بپرس: آخرین بار این مسئله را کی داشتند؟ راه فعلی چیست؟ کدام ورودی واقعی حاضرند استفاده کنند؟ آیا خروجی پیشنهادی قابل‌اعتماد است؟ برای چه convenience/support مشخصی حاضر به پرداخت‌اند؟ قیمت و درآمد را پیش از پاسخ واقعی قطعی نکن.

شرط ادامهٔ سرمایه‌گذاری عمومی: دست‌کم ۳ نفر کار اصلی را مستقل تمام کنند و ۲ نفر برای یک نیاز واقعی دوباره برگردند. اگر مصاحبه/آزمایش ممکن نشد، نسخهٔ شخصی قابل‌استفاده همچنان ارزش دارد؛ market validation را UNVALIDATED نگه دار. وقتی کاربران فقط demo را جالب می‌دانند یا به workflow واقعی وصل نمی‌شود، scope را محدود یا پروژه را متوقف کن.

## MVP لازم

- CSV و Zeek conn.log با schema mapping
- Parquet partition + DuckDB embedded
- baseline آماری قابل‌توضیح
- داشبورد خصوصی و export گزارش

روش عرضه: `embedded-private`. معماری انتخابی: Python FastAPI service/CLI, DuckDB embedded analytics, Parquet immutable partitions, SQLite batch metadata, React UI. ابتدا نسخهٔ خصوصی/محلی قابل‌استفاده و در صورت مناسب‌بودن demo روی دامنه، سپس beta. «آنلاین» بودن به معنی نداشتن storage نیست؛ در این پروژه نگهداری داده به این شکل است:

- **Parquet**: normalized flow partitions and versioned feature snapshots
- **DuckDB**: embedded queries over committed Parquet; single controlled writer for derived catalogs
- **SQLite**: jobs, batch manifests, labels and processing checkpoints
- **Filesystem**: uploads with configured expiry and report exports

سرویس‌های اجباری حذف‌شده نسبت به v7: Laravel, PostgreSQL, ClickHouse, Valkey, mandatory S3. این تغییر معماری در ADR ثبت شده؛ invariants دامنه باید حفظ شوند. بستهٔ v7 در legacy است و مسیر فعلی را تعیین نمی‌کند.

## چه چیزی لازم است تا بالا بیاید؟

- بخش‌های C01–C06 در roadmap، toolchain و سورس واقعی را ایجاد و تثبیت می‌کنند؛ این نسخه runtime اپ ندارد.
- قابلیت‌های C07–C26 دقیقاً رفتار اختصاصی همین پروژه را می‌سازند؛ معیارها در `plans/COMMIT_ROADMAP.md` و JSON آن آمده‌اند.
- C27–C30 امنیت، workload، diagnostics و نصب/restore را برای استفادهٔ شخصی اثبات می‌کنند.
- C31–C40 بستهٔ انتشار، دامنه، UX، beta و انتشار v1 را تکمیل می‌کنند؛ حساس‌ترین features ممکن است فقط private باقی بمانند.
- پیش‌نیاز ظرفیت: private batch host هدف 2–4 vCPU / 4 GiB RAM / 20 GiB SSD؛ نیاز GPU ندارد. هدف 1M row باید benchmark شود. این اعداد بودجهٔ آزمایش‌اند؛ قبل از خرید host benchmark شوند.
- تخمین برنامه‌ریزی برای توسعه‌دهندهٔ متمرکز: 6–10 هفته بدون ML. تضمین زمان نیست؛ بعد از engine proof با سرعت واقعی اصلاح شود. public SaaS و mobile store در این تخمین نیستند.

## ریسک و حدود ادعا

- anomaly مترادف حمله نیست
- دیتاست پژوهشی و packet CSV با flow CSV یکسان نیستند؛ mapping باید بررسی شود
- IP و timestamp دادهٔ حساس‌اند؛ redaction و retention لازم است

## آزمون پذیرش اختصاصی

1. CSV fixture و Zeek را normalize کن و mapping نامعتبر را quarantine کن
2. duplicate/reordered batch شناسه‌های برابر و بدون double count بدهد
3. report از همان partition و feature schema دوباره تولید شود؛ anomaly explanation حاضر باشد

## قابلیت‌های بعدی؛ خارج از انتشار اولیه

- live packet capture روی سرور عمومی
- ClickHouse streaming cluster
- مدل ML production
- IDS/NDR سازمانی real-time

نسخهٔ انگلیسی باید install/use/limitations/support را شفاف کند و خروجی قابل‌حمل داشته باشد. حساب کاربری دائمی، پرداخت و analytics فقط در صورت نیاز واقعی اضافه شوند. دادهٔ حساس واقعی در demo عمومی نباشد. برای mobile app، ابتدا PWA قابل‌نصب ارزیابی شود و سپس اگر نیاز واقعی به native وجود داشت مسیر فروشگاه جدا تعریف شود.

## شواهد بیرونی و مرز استنتاج

- [Zeek conn.log](https://docs.zeek.org/en/current/logs/conn.html): اطلاعات اتصال پایهٔ مناسبی برای واردسازی و گزارش است؛ این منبع صحت تشخیص ML را ثابت نمی‌کند.
- [DuckDB Parquet](https://duckdb.org/docs/lts/data/parquet/overview): Parquet و pushdown پشتیبانی می‌شوند؛ سقف ظرفیت باید روی workload واقعی اندازه‌گیری شود.

منابع بالا قابلیت‌ها و وجود راه‌حل‌های جایگزین را نشان می‌دهند. انتخاب niche، امتیاز، ترتیب ساخت و اهداف آزمایش، استنتاج/پیشنهاد این بررسی‌اند و از منبع به‌عنوان آمار بازار نقل نشده‌اند.
